# Самообновление агента

Актуально для агента 2.5.0. Механизм реализован полностью (агент + сервер)
и провалидирован в проде: агент сам скачивает новый подписанный бинарь,
проверяет подпись и перезапускается.

Код: агент — `internal/agent/selfupdate`; сервер — `FetchUpdateManifest` в
`internal/server/gateway/update_manifest.go` (канальный путь) и `agentVersion` в
`internal/server/api/handler.go` (публичный stable); публикация — `cmd/publish-release`.

## Как это работает

1. Агент запрашивает манифест **своего канала** по gRPC под mTLS
   (`FetchUpdateManifest`, os/arch — GOOS/GOARCH работающего бинаря). Если этот путь
   недоступен (старый сервер, обрыв gRPC), агент откатывается на публичную
   HTTP-ручку `GET /api/v1/agent/version?os=<GOOS>&arch=<GOARCH>`, которая всегда
   отдаёт `stable`. Откат пишется в лог WARN'ом и безопасен по построению: он может
   только не додать канареечной машине beta-версию, но никогда не отдаст beta
   обычной. Расписание проверок общее для обоих путей:
   первый раз — вскоре после старта службы, дальше раз в
   `ROUTINEOPS_UPDATE_INTERVAL` (по умолчанию 6ч). Проверка на старте нужна потому,
   что перезапуск службы и ребут машины иначе отодвигали уже опубликованный релиз на
   весь интервал. Первая проверка идёт с полным jitter'ом
   `[0, min(интервал/10, 5 мин)]` — парк из тысячи устройств после массового ребута
   не должен прийти за манифестом и бинарём одновременно (`startupJitter`).
2. Если `version` новее (semver) и текущей версии, и anti-rollback floor —
   качает бинарь по `url` (сервер раздаёт `releases/` через `/downloads/`;
   лимит скачивания 200 МБ, таймаут).
3. Проверяет **sha256** бинаря и **ed25519-подпись манифеста** публичным ключом
   релиза (агент получает его при enroll; opt-in legacy-сборки могут вшить ключ в
   бинарь). Без валидной `manifest_signature` — отказ (fail-closed).
4. Атомарно заменяет свой бинарь (unix: rename; windows: rename-aside + write).
5. Перезапускается: macOS — launchd KeepAlive; Windows — `os.Exit(1)` → SCM
   FailureActions поднимает службу на новом бинаре
   (`internal/agent/service/run_windows.go`). Работает начиная с агента v2.2.5;
   у ≤2.2.4 чистый stop не триггерил recovery — служба оставалась Stopped до
   ручного старта/ребута.

dev-сборки (`version=dev` или пустая) не автообновляются.

## Включение

В релизной установке самообновление включается само, ничего настраивать не надо:

- **Публичный ключ** приезжает агенту в ответе на enroll (поле `release_pubkey`):
  сервер держит `RELEASE_PUBKEY` в `.env.prod` и отдаёт его при энроллменте, а агент
  сохраняет ключ в файл рядом с CA. `install.sh`/`update.sh` собирают
  **универсальный** бинарь БЕЗ вшитого ключа (`RELEASE_PUBKEY` в `Makefile` по
  умолчанию пуст) — один бинарь на все деплои. Вшивание при сборке (цели
  `make build-win`/`build-mac`/`build-linux` через
  `-ldflags "-X main.releasePubKey=$(RELEASE_PUBKEY)"`) осталось как opt-in для
  legacy/dev-сборок и по умолчанию выключено.
- **URL манифеста** служба получает при `enroll -install-service`: он выводится
  из enroll-URL (`/api/v1/enroll` → `/api/v1/agent/version`,
  см. `deriveUpdateURL` в `cmd/agent/main.go`).

Какой ключ проверяет подпись, решает `resolveUpdatePubKeyB64` (`cmd/agent/main.go`)
по приоритету: (1) ВШИТЫЙ `releasePubKey`, если сборка не универсальная — он
авторитетен и в проде не обходится через env/флаг (SEC-2); (2) ключ, сохранённый при
enroll из доверенного (пин CA) enroll-ответа — это путь универсального бинаря;
(3) `-update-pubkey`/`ROUTINEOPS_UPDATE_PUBKEY` — dev-override ТОЛЬКО для сборок без вшитого
ключа. Остальные параметры работают в любой сборке:

| Флаг | Env | Дефолт |
|---|---|---|
| `-update-url` | `ROUTINEOPS_UPDATE_URL` | пусто = выключено |
| `-update-interval` | `ROUTINEOPS_UPDATE_INTERVAL` | `6h` |
| `-update-pubkey` | `ROUTINEOPS_UPDATE_PUBKEY` | dev-override; игнорируется при вшитом ключе |
| `-update-floor` | `ROUTINEOPS_UPDATE_FLOOR` | `agent_update_floor.txt`; на macOS/Linux служба пишет в `<DataDir>/update_floor.txt` |

## Каналы обновлений и канареечная выкатка (Q-52)

Релиз публикуется В КАНАЛ: `stable` (весь парк) или `beta` (канареечные группы).
Канал — свойство **группы устройств** (`device_groups.update_channel`, миграция 065),
и устройство считается канареечным, если состоит хотя бы в одной beta-группе.
Правило «максимум», а не «минимум»: канареечная группа добавляется меткой поверх
рабочих, иначе любая обычная группа возвращала бы машину на stable.

`beta` — НАДМНОЖЕСТВО `stable`: канарейка видит и стабильные сборки и потому никогда
не оказывается старее парка. Из этого же следует, что продвижение обкатанного билда —
это повторный `publish-release` той же версии с `-channel stable`: строка меняет канал,
пересборка не нужна, канарейка ничего не теряет.

Порядок выкатки на парк:

```sh
# 1. в канарейку
make publish-release BINARY=… OS=… ARCH=… VERSION=v2.6.0 CHANNEL=beta
# 2. смотрим «Выкатка» в панели: канареечные машины поехали, парк на прежней версии
# 3. продвигаем ту же версию на весь парк
make publish-release BINARY=… OS=… ARCH=… VERSION=v2.6.0 CHANNEL=stable
```

Панель: раздел **Выкатка** (`/rollout`, `GET /api/v1/update-rollout`) — по каналу
видно целевую версию и реальное распределение версий агентов. Вторая половина
обязательна: агент обновляется сам и молча, поэтому «канарейка поехала» и «канарейка
поехала и упала, не доложив» различаются только этим.

**Совместимость.** Агенты до 2.6.0 умеют ходить только в публичную HTTP-ручку, а та
отдаёт `stable`. Это и есть нужное поведение: старый парк физически не может попасть
под канареечную выкатку. Обратная сторона — до тех пор, пока парк не перешёл на агента
с канальным путём, канарейка на нём не работает; первая выкатка версии с поддержкой
каналов идёт по-старому, на весь парк.

## Контракт manifest

Канальный путь (основной) — gRPC `AgentService.FetchUpdateManifest` под mTLS:
устройство сервер выводит из CN сертификата (ADR-1), канал — из групп устройства.
Поля ответа те же, что ниже, плюс `channel` (диагностика: из какого канала выдан
манифест; агент его не запоминает и каналом не управляет).

Запасной путь — публичная REST-ручка:

```
GET /api/v1/agent/version?os=darwin&arch=arm64
```
Эндпоинт публичный (без auth) и отдаёт ТОЛЬКО канал `stable`: личности
спрашивающего здесь нет, а значит нет и права выдать канареечную версию. Ответ `200`:
```json
{
  "version":            "v2.4.5",
  "url":                "https://<SERVER_IP>/downloads/agent_darwin_arm64_v2.4.5",
  "sha256":             "<hex sha256 бинаря>",
  "signature":          "<ed25519 над sha256(бинарь) — legacy, для старых агентов>",
  "manifest_signature": "<ed25519 над version\\nos\\narch\\nsha256 — актуальная проверка>"
}
```

- Сервер отдаёт **последний** релиз для os/arch из таблицы `agent_releases`
  (миграции 009 + 019); параметр `current` информационный, гейтинга по
  устройствам нет — все агенты тянут latest в течение интервала.
- `os`/`arch` в ответе не дублируются: агент подставляет свои
  `runtime.GOOS`/`GOARCH` при проверке подписи.
- Агент требует: `sha256(binary) == sha256` И валидную `manifest_signature`.
  Пустая `manifest_signature` → отказ, даже если legacy `signature` валидна.

### Почему подписывается манифест, а не только бинарь

Подпись только `sha256(binary)` защищала бинарь, но не связь версии с бинарём:
скомпрометированный сервер мог отдать СТАРЫЙ валидно подписанный бинарь под
произвольной `version` — агент счёл бы его новым и откатился на уязвимый билд.
Канон `version\nos\narch\nsha256` (newline-разделитель, фиксированный порядок)
закрывает это. Подписывает `cmd/publish-release`, проверяет
`internal/agent/selfupdate/selfupdate.go:signedMessage`/`verify` — PureEdDSA,
без префиксного хеша.

### Anti-rollback floor

Подпись не спасает от replay СТАРОГО, но настоящего манифеста (легитимный v3.0,
отозванный после уязвимости, технически валиден вечно). Поэтому агент держит
high-water mark — файл с максимальной версией, которая на этой машине **уже
работала** (`-update-floor`). Манифест обязан быть новее и текущей версии, и
floor. См. `Updater.loadFloor`/`confirmRunning`.

🔴 **Пол поднимает ЗАПУСК версии, а не замена файла** (исправлено 11.08.2026).
Прежде `saveFloor` стоял сразу после успешной подмены бинаря, и это давало
тихий вечный отказ: если замена удалась, а новая версия не поднялась (инцидент
с подписанным мусором 10.08.2026, битая сборка, несовместимая DLL, сбой на
старте), пол уже стоял на версии, не прожившей ни секунды. Дальше:

- машина отказывалась принимать эту версию, **включая исправленную пересборку
  под тем же номером** — лечилось только выпуском следующего номера;
- штатное восстановление (вернуть бинарь из `<exe>.old`) пола не касается,
  то есть процедура отката и анти-роллбек противоречили друг другу;
- в логе не было НИ ОДНОЙ строки: ветка «не новее» одинаково молчала и про «мы
  уже актуальны», и про «мы заперты полом».

Сейчас пол пишется в `confirmRunning` — при первой успешной проверке манифеста,
то есть когда версия доказала, что служба поднялась и канал до сервера жив.
Отказ по полу печатается предупреждением со всеми числами и путём к файлу.
Защита SEC-3 от этого только усиливается: ручной откат бинаря вниз пол
по-прежнему переживает, а версия, которой машина не видела в работе, в пол уже
не попадает; заодно покрыта подмена бинаря мимо self-update (переустановка
MSI/PKG) — она тоже поднимает пол, потому что версия работает.

**Порог живучести — первая проверка, а не «версия стабильна».** Право поднять пол
даёт первая успешная проверка манифеста, а она приходит через `startupJitter`
(`[0, min(интервал/10, 5 мин)]` от старта службы). Значит версия, которая
поднялась, прожила несколько минут и только потом ушла в crash-loop, пол
поднимет. Это осознанная граница, а не недосмотр: она отделяет «легло на диск» от
«работало», чего и добивался фикс, а полноценное подтверждение живучести
(N успешных циклов, окно наблюдения) — отдельная механика, которая дороже
проблемы. Практическое следствие для оператора: **машину, упавшую в crash-loop не
мгновенно, а через минуты, всё равно надо чинить следующим номером версии** либо
правкой пола руками.

**Если пол ложный** (записан агентом до фикса, версия из него никогда не
работала, либо версия проработала минуты и развалилась): вписать в файл
работающую версию или удалить файл. Путь — в строке лога и в таблице путей выше.

**`<exe>.old` на Windows** удаляется не при старте, а вместе с подтверждением
версии (`DropPrevious`). Агент, который поднимается и падает через две секунды,
раньше успевал снести единственный путь восстановления до того, как сломаться.
На macOS/Linux запасного файла нет вовсе — `os.Rename` переставляет бинарь одним
шагом, и восстановление там означает переустановку пакета.

## Публикация релиза

**Self-hosted:** `./update.sh` делает всё сам — бэкап БД → `git pull` →
пересборка (compose-сервис `migrate` накатывает миграции до старта server) →
сборка и публикация агентов windows/amd64, linux/amd64, darwin/arm64 с подписью
per-deployer ключом `release_ed25519.pem` (его создаёт `install.sh`).

**Вручную** (ключ по умолчанию `RELEASE_KEY=~/release_ed25519.pem`):

```sh
make build-win VERSION=$(cat AGENT_VERSION)
make publish-release BINARY=bin/agent_windows_amd64.exe OS=windows ARCH=amd64 VERSION=v$(cat AGENT_VERSION)
# эквивалент: go run ./cmd/publish-release -binary … -version … -os … -arch … -key …
```

`publish-release` считает sha256, подписывает бинарь и канон манифеста,
копирует бинарь в `releases/` и пишет запись в `agent_releases`. Повторная публикация той же
`(os,arch,version)` с ТЕМ ЖЕ sha256 не падает и меняет только канал — это и есть продвижение
beta→stable. С ДРУГИМ sha256 — отказ: версии неизменяемы, перезалить байты под тем же номером
нельзя (иначе подписанный манифест обходится изнутри).

Флаг `-channel` (`stable` по умолчанию, `beta` — канарейка) выбирает канал выкатки.
Дефолт именно `stable`, а не `beta`: команду запускают руками, и забытый флаг должен
вести себя как раньше, а не тихо посадить релиз в канарейку, откуда его никто не ждёт.

Генерация ключа (один раз; для self-hosted это делает `install.sh`):

```sh
openssl genpkey -algorithm ed25519 -out release_ed25519.pem   # приватник — у деплойера/в CI secrets
# raw 32-байтный публичный ключ base64 — это RELEASE_PUBKEY: сервер кладёт его в
# .env.prod и раздаёт агентам при enroll (и он же — значение для opt-in вшивания):
openssl pkey -in release_ed25519.pem -pubout -outform DER | tail -c 32 | base64
```

## Редакция публикуемого агента

Агент, который раздаёт канал self-update, обязан быть той же редакции, что и
инсталляция. Это не косметика: в open-core сборке FileVault не «выключен», а **не
скомпилирован**, поэтому мак, обновившийся на open-core агента, на команду
provisioning ответит отказом навсегда.

`update.sh` берёт редакцию из `BUILD_TAGS` в `.env.prod` (той же переменной собирается
серверный образ) и передаёт её в сборку windows/linux-агентов. `install.sh` — то же
самое, но переменную он читает из окружения/`install.env`. Раньше install.sh собирал
агентов безусловно без тегов: свежая enterprise-инсталляция раздавала парку open-core
агента до первого `update.sh`.

**Проверяется собранный бинарь, а не переменная.** После каждой сборки и перед подписью
идёт `scripts/agent-edition-guard.sh`: он ищет в бинаре путь пакета
`internal/agent/screen`. Пакет линкуется только под тегом `enterprise` (единственный
импортёр — `cmd/agent/screen_wiring.go`), и токен переживает `-trimpath` и `-s -w`.
Расхождение в любую сторону останавливает публикацию:

| инсталляция | бинарь | что делает гейт |
|---|---|---|
| enterprise | open-core | отказ: парк потерял бы `screen_session` → 409 `agent_unsupported`, FileVault отказывал бы навсегда |
| open-core | enterprise | отказ: раздача закрытого кода всему парку |

Переменную можно забыть при переносе окружения, символ забыть нельзя. Тот же скрипт с
обратным ожиданием стоит на трекнутых артефактах в `scripts/check-installer-versions.sh`
и в `make check-remote-tags` — они обязаны быть open-core ВСЕГДА.

Токен именно пакета экрана, а не darwin-only маркера (как было в проверке macOS-бинаря):
такой токен на enterprise-сборке windows/linux отсутствует, и гейт был бы красным на
исправном дереве.

macOS-бинарь собирается не здесь (нужен cgo и мак), поэтому для него правило такое:

- **open-core инсталляция** — публикуется `build/darwin/agent_darwin_arm64` из
  репозитория. Если этот файл окажется enterprise-сборкой, публикация отменяется:
  это была бы раздача закрытого кода всему парку.
- **enterprise инсталляция** — публикация из репозитория запрещена (там всегда
  open-core: enterprise-бинарь нельзя коммитить, его ловит гейт публичного среза).
  Нужен артефакт из приватного релиз-канала:

  ```sh
  # положить рядом с деплоем: бинарь + .sha256 + .version
  DARWIN_AGENT=enterprise/agent_darwin_arm64 ./update.sh
  # первая установка — та же переменная:
  DARWIN_AGENT=enterprise/agent_darwin_arm64 ./install.sh
  ```

  Путь указывается ОТНОСИТЕЛЬНО каталога деплоя — контейнер сборки видит только его.
  Проверяется всё то же, что и для репозиторного prebuilt (sha256 и вшитая версия),
  плюс что бинарь действительно собран с тегом enterprise.

Без `DARWIN_AGENT` на enterprise-инсталляции публикация macOS отменяется целиком, а не
подменяется open-core агентом молча.

## Как проверить

- Манифест: `curl 'https://<SERVER_IP>/api/v1/agent/version?os=windows&arch=amd64'`.
- Версия агента на устройстве: колонка «Версия агента» в UI
  (`devices.agent_version`, миграция 025) или лог службы.
- Быстрее всего — перезапустить службу: проверка идёт на старте (в логе строка
  `selfupdate: первая проверка после старта через …`). Иначе ждать до 6ч либо
  временно уменьшить `ROUTINEOPS_UPDATE_INTERVAL` у службы.

## Восстановление машины, на которой обновление не поднялось

Симптом: служба не стартует после самообновления (битый или подменённый бинарь,
несовместимая сборка). На Windows рядом лежит прежний бинарь — он и есть путь
назад. Из-под администратора:

```powershell
$d="C:\Program Files\RoutineOps"
Copy-Item "$d\RoutineOps-agent.exe" "$d\RoutineOps-agent.exe.broken" -Force  # улику сохранить
Copy-Item "$d\RoutineOps-agent.exe.old" "$d\RoutineOps-agent.exe" -Force
sc start RoutineOps-agent
```

⚠️ `(Get-Service …).Status` без прав на перечисление служб **врёт** (отдаёт
`Stopped` при живой службе) — авторитетно только `sc query RoutineOps-agent`.

**Про пол анти-отката.** Агенты 11.08.2026 и новее пол при этом не портят —
он остаётся на версии, которая работала (см. «Anti-rollback floor»). У агентов
СТАРШЕ этой даты пол успевал подняться до версии, которая не запустилась: тогда
после восстановления в `<DataDir>\state\update_floor.txt` останется чужой номер,
и та же версия (в том числе исправленная пересборка под тем же номером) приниматься
не будет — молча. Проверить и поправить:

```powershell
type "C:\ProgramData\RoutineOps\state\update_floor.txt"   # что стоит
Set-Content "C:\ProgramData\RoutineOps\state\update_floor.txt" "v2.6.6"  # работающая версия
```

На macOS/Linux запасного бинаря нет вовсе (`os.Rename` переставляет файл одним
шагом) — восстановление там означает переустановку пакета.

## Безопасность (зафиксировано в коде)

- Приватный ключ релиза в агенте/на сервере отсутствует — только публичный.
- Манифест без валидной `manifest_signature` НЕ применяется (fail-closed).
- Anti-rollback floor: манифест ниже версии, которая уже работала на машине,
  отклоняется, даже если подпись валидна. Пол поднимает запуск версии, а не
  замена файла (см. выше), а отказ по полу пишется в лог.
- Публичный ключ проверки приезжает при enroll по доверенному каналу (пин CA); в
  универсальной сборке он НЕ вшит. Если ключ всё же вшит (opt-in legacy), он
  авторитетен и не переопределяется env/флагом (SEC-2).
- Лимит размера скачивания (200 МБ), таймаут на загрузку.
- Бинарь недоверен по дизайну — канал раздачи может быть любым, подлинность
  гарантируют sha256 + ed25519.
